## Native source admission experiment: T95/T96

The [offline mapping prototype](../../tests/prototypes/follower_mapping.lua)
wraps public setup only, retaining exact ownership and restoring it on detach.
It scopes mapping to the default set's native automatic Dungeon Assistance row.
Actual ConsolePort AddSecureAction has three distinct inputs/outputs:

1. The original source row remains an automatic spell row in Data.
2. LAB SetState still receives the original spell type and spell ID.
3. Only the compiled restricted DATA slot receives the existing native binding
   map's macro metadata for the named proxy.

This avoids both replacing saved identity and turning the LAB widget into a
custom widget with generic feedback. It does not make a new dispatcher.

Five actual native refresh/auto-assignment cycles retain source bytes and no
duplicate automatic row. Actual native removal when the spell appears on an
action bar preserves the manual row and other sets; re-entry maps the new
automatic row. A single-row actual ring gesture composes the separated state
and DATA into one native toggle request under the existing macro model.

Actual Forever shared admission is seeded with the existing manual choice as
its bootstrap requires. Automatic rows stay outside the manual archive. Manual
default rows and personal/account sets are not routed through the prototype.
Unready routing returns to the ordinary native spell; detach restores public
setup owners, and a foreign replacement is not overwritten. Installation in
combat is rejected.

Four controls deliberately corrupt source identity, switch LAB to custom,
escape the default-set scope, or ignore readiness. Each must be rejected.
The proxy's engine authority and lifetime remain unqualified; this is an
admission result, not a complete execution adapter.

## Actual restricted authority experiment: T97/T98

The full pinned RestrictedFrames.lua and RestrictedEnvironment.lua execute
alongside the already pinned restricted compiler. Their existing native
manifest hashes are verified before loading. Frame metatables/handle lookup,
protection flags, combat and securecall are explicit C/engine doubles.

The executed source demonstrates these boundaries:

| Proposed shortcut | Source result |
| --- | --- |
| Read a mirrored spell attribute from an unprotected handle in combat | GetHandleFrame rejects the handle. The same read works outside combat. |
| Read the native button's arbitrary spellID Lua field through a restricted handle | No such field is exposed. |
| Ask a public GetSpellID method through CallMethod and use its result securely | The return value is discarded. |
| Repair a protected mirrored attribute through a public callback in combat | CallMethod forces the callback insecure; the modeled protected write is rejected and the old identity remains. |
| Invoke CastSpellByID directly from a restricted snippet | The actual restricted global whitelist does not expose the API. Compilation alone is not authority; execution does not cast. |
| Add tryToggleSpell/toggle attributes to an ordinary secure spell button | The actual secure spell handler ignores them and still issues its two-argument request. |

Three controls remove the combat-handle check, remove CallMethod's forced
insecure boundary, or inject a cast API into the whitelist. Each must fail the
baseline's expected boundary assertion. None grants new permission in Retail.

The C protection flags of the user's actual native frame have not been read.
Testing both relevant model cases does not establish those flags. A protected
button alone would also not prove a stable spell identity: its native content
can change while public protected reconfiguration is deferred.

## Native presentation experiment: T99/T100

The [offline view prototype](../../tests/prototypes/follower_presentation.lua)
decorates only an owned widget's existing ConsolePort texture setter. It
preserves the original setter, native function/atlas cleanup and LAB spell
feedback getters. It does not replace GetSpellTexture globally or change
protected action fields.

Actual locked LAB GetTexture/GetCooldownInfo/GetChargeInfo, ConsolePort's
SkinUtility.SetTexture and Blizzard's zone Refresh execute. Synthetic C icon
values change through repeated lead/stop-style transitions; later generic LAB
redraws still show the zone icon. The candidate follows native override
resolution, stops applying on widget reuse/other active sets/types/readiness,
and falls back on opaque icon data. Native cooldown/charge getters retain the
same objects. Function textures unmount before returning to numeric artwork;
foreign setter ownership is preserved on detach.

Three controls restore the generic icon, escape the widget scope, or bypass
ConsolePort's native texture composition. Each must be rejected. Actual pixels,
events/loading integration and protected dispatch are not established. No new
polling worker or timer is used by this prototype.

## Why another offline cast model would not select a repair

The input matrix already executes ordinary paired gestures with and without
Forever, both ring modes, sticky/neutral selection, combat, modifiers, separate
acceptance and repeat/reopen cases. The user confirmed release selection. Those
ordinary gestures do not duplicate calls. An explicitly added extra release
does; this is a conditional failure, not an observed hardware event stream.

CastSpellByID in the harness records calls and arguments. Teaching that spy to
reverse a follower when the third argument is absent would assume the suspected
answer. More repetitions of the same model cannot establish the C/server toggle
semantics or whether another release occurred in the real client. The same
limit applies to fabricating a pool lifetime guarantee or a macro permission
result. No matching command-toggle fix was found in the selected primary-source
searches; [ConsolePort issue 109](https://github.com/seblindfors/ConsolePort/issues/109)
concerns raid-cursor targeting instead.

The generic spell path may need a narrow input repair if extra dispatch is
observed; delegation may be unnecessary in that case. If one request behaves
differently from the native button, a native-equivalent toggle route needs
Retail qualification. Choosing either now would be a speculative execution fix.
